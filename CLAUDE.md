# CLAUDE.md

Guidance for Claude Code working in this fullstack template.

## Stack

- **Backend**: Django + DRF. API in `api/` (v1 in `api/v1/`). `core/` = project config (settings/urls/wsgi) + shared abstractions only (`BaseModel`, `AppSetting`, payments, utils). **Domain models do NOT go in `core` — each context gets its own app** (see [App structure](#app-structure-where-models-go)). Token auth (`rest_framework.authtoken`). Package mgmt via `uv`.
- **Frontend**: React + Vite SPA in `frontend/`, routing by TanStack Router (file-based, `frontend/src/routes/`), state by Jotai. Package mgmt via `pnpm`.

## App structure (where models go)

**One Django app per domain context. A new model = a new (or existing) domain app, NEVER `core`.**

- Create it: `uv run manage.py startapp <name>` at repo root (top-level, sibling to `core/` and `api/`), add `"<name>"` to `INSTALLED_APPS` in `core/settings.py`, then `make mmg && make migrate`.
- Name apps by context (`accounts`, `billing`, `projects`), not by layer. Domain models subclass `BaseModel` from `core.models` for ObjectId PK + timestamps + `actor`.
- `core` is reserved for project config and cross-cutting shared code only (`BaseModel`, `AppSetting`, payments, utils). Do **not** add feature/domain models to `core/models.py`.

## API conventions (read before adding endpoints)

API modules live in `api/v1/{resource}_api.py`. Use class-based `from rest_framework.views import APIView` (one `APIView` subclass per resource), wired in `api/v1/urls.py` via `.as_view()`, serializers centralized in `api/v1/serializers.py`.

- **A `{resource}_api.py` view may only define the four standard CRUD methods: `get`, `patch`, `post`, `delete`** (retrieve/list, update, create, destroy on that resource). No other HTTP methods belong here.
- **Clean-REST collapse**: the four verbs collapse onto ONE `APIView` served at a canonical route pair — `/{resource}/` (GET list, POST create) and `/{resource}/{id}/` (GET retrieve, PATCH update, DELETE destroy). Both routes point at the same `.as_view()`; methods branch on `pk`. No per-action routes.
- **Everything else goes to `api/v1/{resource}_extras_api.py`** — one extras file per resource, sibling to its `_api.py`, wired in the same `urls.py`, also `APIView` classes. "Everything else" = custom / RPC-style actions that aren't plain CRUD on the resource: auth flows (`login`, `register`, `logout`, `google`), webhooks, bulk / aggregate / side-effect endpoints.

```python
# api/v1/projects_api.py
from rest_framework.views import APIView
from rest_framework.response import Response

class ProjectAPI(APIView):
    def get(self, request, pk=None):  # pk → retrieve, else list
        ...
    def post(self, request):          # create
        ...
    def patch(self, request, pk):     # update
        ...
    def delete(self, request, pk):    # destroy
        ...

# api/v1/urls.py — verbs collapse onto one view, two routes
path("projects/", ProjectAPI.as_view(), name="api-v1-projects"),
path("projects/<str:pk>/", ProjectAPI.as_view(), name="api-v1-project-detail"),
```

`<str:pk>` because `BaseModel` uses an ObjectId PK. Custom actions (`POST /projects/{id}/archive/`, `POST /projects/import/`) go to `projects_extras_api.py`, not here.

> Existing `auth_api.py` / `payments_api.py` use the older function-based `@api_view` style and predate this rule. `auth_api.py`'s custom endpoints (`login`/`register`/`logout`/`google`) are the canonical example of what now belongs in an `auth_extras_api.py`. Leave both as-is unless you're touching them for another reason.

## Armor builder (public, no login)

- Page: `/` → `BuilderPage` in `frontend/src/features/builder/`. Build state is `buildAtom` (`state.ts`, persisted to localStorage under `build`); every number on screen comes from the pure `computeTotals` in `totals.ts`, checked by `pnpm test` (plain `node`, no test runner).
- Data: `GET /api/v1/{skills,set-bonuses,armors,decorations,charms,monsters,weapons}/` — list-only catalog views in `api/v1/{resource}_api.py`. The whole catalog is fetched once (`useCatalog`) and filtered in the browser.
- **Public views set `authentication_classes = []`, not just `AllowAny`.** `TokenAuthentication` raises 401 on a bad token before permissions run, so a visitor with a stale token in localStorage would be locked out of a "public" page. The frontend also passes `skipAuth: true`.
- Granted skills serialize as `{skill: <id>, level}` via `source="skill_id"`, so prefetching the through rows is the only extra query. `api/v1/tests.py` pins what each list costs in `CATALOG_QUERIES`: 1 for a plain list, 2 for decorations and charms, 4 for armors (the two more are `hunts`, below).
- Set bonuses hang off the **piece**, not a set: `Armor.set_bonus` (FK) + `SetBonus.tiers` (`[{pieces, skill}]`, `effects[i]` describes `tiers[i]`). Pieces of different sets feed one bonus (Rathalos α + Rath Soul β → Rathalos Mastery), so there is no `ArmorSet` table. Both fields come from `.dataset/sets.json` via `load_sets` — the last step of `seed`, and it relinks from scratch on every run. The file is `sets.json`, not `armor_sets.json`: `load_armors` globs `armor_*.json`.
- Master Rank armor is `.dataset/armor_{part}_mr.json` (839 pieces, rarity 9-12): a second file per part, which `load_armors`' glob picks up, the part still coming from the file's `type` key. The rows are the wiki's `Master_Rank_{Head,Chest,Arms,Waist,Leg}_Armor` list pages (`Leg`, not `Legs`) plus 16 pieces those pages leave out but the wiki has a page for (Rimeguard γ+, Demonlord α+, Shield-Weaver +, Pearlspring α+). **The values are not the wiki's as scraped.** About 1% of its fields are wrong (rows copied from a neighbour, α+ pages cloned from β+), and its piece and set pages repeat the list page's mistakes, so every field was settled against two datasets that are not the wiki: mhw-db.com and Gathering Hall Studios' MHWorldData. Where those two agree they overrule the wiki: 71 fields on 63 pieces, and five piece names (`Anjanath Vambraces` is `Anja Vambraces`). Scraping the list pages again on their own brings the errors back. 15 pieces (Direwolf, Golden Lune α+/β+) are in a base file too: the `_mr` file sorts after its base file, so it loads second and wins, and it keeps the base file's spelling of the name (`Golden Lunehelm Alpha+`, no space) because the loader upserts on name.
- Weapons are `weapons.Weapon`, loaded by `load_weapons` (part of `seed`). The builder gets 11 of its fields and holds one weapon (see Weapon, below); the url, elderseal and sharpness are data only. `.dataset/weapon_{type}_mr.json` is 14 files, 1,792 Master Rank weapons (rarity 9-12), the type coming from each file's `type` key as with armor. **The values are the game's, not the wiki's.** The rows start from the wiki's `Master_Rank_Weapons` page (1,297 of its 1,298: `Purgation's Atrocity` is High Rank), but that page is far worse than the armor pages: 355 fields on 312 weapons are wrong (the hidden-element parentheses missing on 162, slots on 55, attack on 40, the Safi'jiiva weapons shown awakened) and 15 names are misspelt (`Usuper's Lightning`, `Deep Terrior`). mhw-db.com stops at rarity 8, so the two datasets that settle a weapon are MHWorldData (`weapon_base.csv` + `weapon_sharpness.csv`) and Kiranico (`/en/weapons?type=0..13`). They disagree on 8 fields of 6 weapons, and mhw.poedb.tw, a third datamined site, sided with Kiranico on every one. Added to the page's rows: 34 weapons it leaves out (every Fatalis weapon), 4 that MHWorldData lacks too but Kiranico, poedb and a wiki page have (`Azure Era "Soaring Dragon"`), and the 457 Kulve Taroth weapons. **Kulve attack and element are the fully upgraded numbers, from MHWorldData alone**: Kiranico and the wiki show the weapon before its upgrade levels. The check that they are not typos is that the gap is one fixed bonus per weapon type and rarity across all 457. Names are the game's: `Tiger Jawblade+` without the wiki's space, `Kjárr` with its accent, so a search box has to fold it. Three PlayStation-only Horizon weapons (`Aloy's Adept War Bow`, `Stormslinger Prototype`, `Adept Stormslinger`) are on the wiki alone and could not be checked. Left out: 14 rarity 11 weapons, one per type, that only the datamined sites list (`Hunter's Knife`, `Artemis's Dual Blades`) and the wiki has no Master Rank page for. `sharpness` is red to purple in the game's units (a full bar is 400) and `sharpness_max` the same bar at Handicraft 5. `skill` is a name, not a link, because it is a skill (Critical Element), a set bonus (Kulve Taroth Essence) or a set-bonus skill in neither table (Guts).
- Monsters are `monsters.Monster` and `monsters.MonsterDrop`, loaded by `load_monsters` (part of `seed`, after `load_items`). The API lists the monsters themselves (`id, name, type, species`) for the set search's unslain list; the drops have no API view, and reach the builder only as an armor's `hunts`. `.dataset/monster_{large,small}.json` is 94 monsters, 71 large and 23 small, the type coming from each file's `type` key, with their drops nested under them: 5,852 rows in 1,775 tables. A drop is a `rank` (`low`, `high`, `master`: the first model here that stores one), a `method` (17: carve, break, mine, shiny drop, track, plunderblade, palico, bandit mantle, quest reward, investigation silver / gold / purple, Guiding Lands low / mid / high / tempered, siege reward) and, for a carve, a break or a mine, a `part` in the game's words (`""` is the body, `tail` the severed tail), then the item, its quantity and its chance in percent. A table is the rows that share monster, rank, method and part, and it adds up to 100 — but for Shara Ishvalda's two leg mantles, at 200: the game keeps two tables under each label and nothing says which break pays which. A table can hold one item twice, at two quantities, so the uniqueness constraint is the whole row. **Capture is not a method**: on the 51 monsters MHWorldData marks as trappable, Kiranico's capture table is its carve table in all 89 monster-and-rank pairs, so capturing pays from `carve`. Kestodon is two rows, `Kestodon (Male)` and `Kestodon (Female)`: both dumps give them different carve tables, and they share the wiki's one page. Gajalaka and Boaboa have no drops: theirs are item tables (rations, throwing knives) that no source labels.
- **The drop numbers are the game's; the wiki supplies only the roster, links and icons** (its `Monsters` page, which is the `Large_Monsters` and `Small_Monsters` pages transcluded, less Grimalkyne). It could not supply more: 19 of its 71 large-monster pages have no percentage on any row, and quantities are mostly missing. The numbers come from three datamined sources, MHWorldData (`monster_rewards.csv`), Kiranico (`/en/monsters`, 95 pages) and mhw.poedb.tw (`/eng/monsters/{large,small}`, 94 pages), and 1,533 of the 1,775 tables are the same in all three. **"Two against one" does not settle the rest**, as it did for armor: MHWorldData names the other two among its own sources, so its siding with one of them proves little. Kiranico and poedb are two extractions of the game files with different defects, so where the two agree they set the numbers, and they overrule MHWorldData on 33 tables: the purple investigation reward of the 14 Master Rank monsters at threat level 3 (Sealed Feystone 80 / Carved 20, where it has 40 / 60), Furious Rajang's silver and gold investigations, Zorah Magdaros's quest reward and 15 small-monster quest rewards. But both dumps also print tables the game never pays out, so **which tables exist** is MHWorldData's word or a rule. A track or investigation table has to be in MHWorldData: 24 are left out, both dumps having investigation rewards for Zorah Magdaros, Xeno'jiiva, Kulve Taroth, Safi'jiiva, Shara Ishvalda, Raging Brachydios and Behemoth, which MHWorldData gives none. A rank needs two of MHWorldData's rows, poedb's rank line and a quest on Kiranico (out: Deviljho at Master Rank, Nergigante at Low Rank). A Guiding Lands table needs the monster on Kiranico's Guiding Lands list, which the wiki's Guiding Lands page matches (out: the tables the dumps carry for Jyuratodus, Frostfang Barioth, Furious Rajang and Raging Brachydios). 48 tables stand on one source. 40 on Kiranico: 32 palico tables, Iceborne monsters' and Behemoth's, which the other two list for base-game monsters only, where Kiranico's matched on every one but Zorah Magdaros's; Behemoth's plunderblade; Scarred Yian Garuga's carve, three breaks and quest reward, which the wiki's page, one that has percentages, confirms but for two fields; Leshen's and Master Rank Kulve Taroth's quest rewards, which Kiranico files as a bronze investigation reward, its hunt table being a placeholder, and the wiki's reward lists name item for item. 4 on MHWorldData: Barroth's head shell carve at Low and High Rank, Kelbi's horn as a shiny drop. 4 on a poedb table with no label, named from the monster's lower ranks or its neighbours: at Master Rank, Barroth's head shell, Radobaan's and Uragaan's back mining, Hornetaur's carve. **Scraping either dump again needs its defects known.** Kiranico: a `Monster Bone L 100%` placeholder wherever a table does not exist; tables for ranks a monster has no quest in; the four Guiding Lands tables repeated under a "Capture" label; event-quest tables under the ordinary label (the second head-break table of Zinogre and Brute Tigrex); Zorah Magdaros's bandit mantle and palico labels swapped; Shara Ishvalda's head carve under "Tail Carved"; every Kulve Taroth table called "Carves" (three are kept, as poedb names them; 11 are left out). poedb: no body-carve table, only the capture one, which differs for five elder dragons; separate tables merged under one label; its last pages shifted (Frostfang Barioth's shows Fatalis's capture, break and hunt tables, Scarred Yian Garuga's shows Frostfang Barioth's); 13 track rows that are another table's; small monsters' Master Rank carves under the Low Rank heading; and bare `condition N` labels, used here only to witness a table another source names.
- A monster's `weaknesses` is a JSON list of forms, each the stars (0-3) for five elements and five ailments: the first is the monster as the fight starts, the rest a state it can be in (`covered in mud`, `charged`, `emitting light`). 9 monsters have more than one, and Alatreon's three are all states (`fire active` first). They are MHWorldData's (`monster_weaknesses.csv`), checked against the wiki (the infobox for elements, the page's ailment table), poedb's large-monster list and mhw-db's 42 monsters. 7 values on 3 monsters are overruled, each by two of those: Anjanath's dragon and poison, Tigrex's fire and water (swapped), and three ailments of Ancient Leshen, which had Leshen's row. poedb's list has Barroth's, Bazelgeuse's and Tzitzi-Ya-Ku's rows under Behemoth, Leshen and Ancient Leshen. Where MHWorldData leaves an alternate form's ailments blank they are the first form's; its "elderseal efficiency" form for Safi'jiiva is left out, being no state of the monster. Small monsters have `[]`: nothing rates them. Species is unanimous across four sources for the large monsters; for the small ones it is the wiki's and mhw-db's, 7 on one of the two alone, and Gajau is a `fish` (its own wiki page and mhw-db) though the wiki's list calls it a piscine wyvern.
- Items are `items.Item`, loaded by `load_items`: `.dataset/items.json` is 961 items and nothing else: the 852 things the drop tables name, and the 109 that only an armor recipe names (37 tickets, 21 coins, 17 bones, 15 crystals, `Meldspar Ore`, `Commendation`). So no item that neither a monster drops nor an armor is forged from, which leaves out the charm ores (`Dreamcore Ore`). The file is not `monster_items.json`: `load_monsters` globs `monster_*.json`, the `sets.json` trap again. Names are the game's (`Rath Wingtalon+`, which the wiki's Rathalos page calls `Rathalos Wingtalon+`), and MHWorldData and Kiranico spell them alike, all but `Bluegleam` and `Daemon Ticket`, which are PlayStation-only and in neither. The wiki's page for an item is the name with `+` spelt out (`Rath_Wingtalon_Plus`); 6 have none, and their `url` is `""`. **A drop or a recipe line that names an item not in the file is an error that rolls the load back**, not a stub like the one `load_armors` makes for a skill: a stub would need a rarity and a price, and the likely cause is a wiki spelling turning into a second item. Rarity and sell price are settled between MHWorldData (`item_base.csv`), Kiranico's item pages and mhw-db's `/items`, the wiki's infobox only breaking a tie. For the 852 dropped items every source that has a value agrees on 843 rarities and 832 prices, mhw-db is the odd one out on 7 rarities and 4 prices, MHWorldData on 1 (Fatalis Evil Eye is 12), and the wiki's infoboxes are wrong on 45 fields of 36 items (`Rathalos Carapace` sells for 1,850, not 185). For the 109 recipe items the datamined sources agree on both fields of 106; `Fun Fright Ticket` is MHWorldData's and the wiki's, and the two PlayStation items are mhw-db's and the wiki's. 25 of the 964 Kiranico item pages fetched open another item's (23 of the dropped items', `Effluvial Crystal`, `Fun Fright Ticket`; the 964 are every item here but the two PlayStation ones, and 5 that only armor the dataset lacks is forged from): its ids differ only by letter case (`edbJr`, `edBJr`) and it looks them up ignoring case, so check the page's title against the item. `sell_price` is zenny, and it is 0 for 13 items, for two reasons. Six are account items (Wyvern Tear, Dragon Treasure, White Liver): the game turns them into research points, and that number of points is what Kiranico and the wiki show as their price. Seven cannot be sold (`Commendation`, `High Commendation`, `Conqueror's Seal`, both Research Commission Tickets, `Steam Ticket`, `Thermae Ticket`): Kiranico and mhw-db both say 0 and MHWorldData leaves the price blank. The six Fatalis materials' prices are Kiranico's, MHWorldData leaving them blank, and the wiki agrees on five. `Charm.materials` is not linked to items and still holds the wiki's names: 267 of its 317 are an item here, 13 are game items that are in neither a drop table nor an armor recipe (the six `-core Ore`s, `Deepsea Crystal`), and 37 are spellings of the wiki's own (`Tempered Rathalos Scale` is `Tempered Red Scale`; `Tempered Tigex Jaw`).
- `Item.gathered` says no one monster has to be hunted for the item, and it is a key every row of `items.json` carries, like the rest. **It cannot be read off the drop tables**, which name ore and bone too: mining Uragaan's back gives `Carbalite Ore`, Kulve Taroth's siege pays `Fucium Ore`, and Tigrex's hunt reward is the only table with `Monster Slogbone`. 67 items have it, on three kinds of evidence. 34 have a labelled row on their Kiranico page (`Mining Outcrop`, `Bonepile`, and the `Upsurge:` of each: 31 items) or a row in MHWorldData's gathering table (`source_data/locations/location_items.csv`: 21 items here, 18 of them in both; it stops at the base game's five locales and lacks even `Earth Crystal`, so a missing row says nothing). `Dragonvein Crystal`, `Honey` and `Nulberry` are MHWorldData's alone, `Golden Chunk` and `Golden Fragment` (the Caverns of El Dorado's outcrops) Kiranico's alone, their wiki pages being placeholders. 27 are the Guiding Lands' 26 crystals and bones and `Spiritvein Crystal`: Kiranico lists them under a locale with **no label**, and the game's own description, which the wiki quotes, says where they are from (`Ore obtained in the Guiding Lands' coral region`, `Mined from master rank areas`). `Effluvial Crystal` stands on that description alone, its Kiranico page opening another item's. A blank label is not evidence by itself: 89 items have such rows, monster parts among them (`Great Jagras Scale | Ancient Forest | 70%`). The last 6 are **not gathered at all**: the generic bones `Monster Bone L`, `Monster Bone+`, `Monster Keenbone`, `Monster Toughbone`, `Monster Slogbone` and `Monster Solidbone`, which the game calls "bone obtained from large monsters" and which quests pay whatever their target. The measure is the quests that pay an item though none of their targets drops it, and how many different monsters those quests are for: 60 quests of 28 monsters for Toughbone, 50 of 24 for Slogbone, 38 of 17 for Solidbone, 24 of 11 for Keenbone, 22 of 9 for Bone+, 15 of 7 for Bone L. The quests are the item page's, which Kiranico and poedb (`/eng/item/{id}/{name}`, the "Obtaining Quest" card) list alike for every one of the 71 items compared; the targets are poedb's quest lists (`/eng/quests/{1..16}` and the named ones), which name none for 39 of their 511 quests, and those quests are not counted. The same measure keeps the flag off what looks alike: `Monster Hardbone`, `Elder Dragon Bone`, `Elder Dragon Blood` and the sacs have no such quest (the quests that pay Hardbone are its eleven monsters' own), and `Large Elder Dragon Bone` and `Pure Dragon Blood` have six, all of them Alatreon's, Fatalis's or Kulve Taroth's: three more elder dragons, not a way round one. `Lava Nugget` and `Wyvern Bonemass` are in a mining table and are the monster's own. **False means no source shows a way round the hunt, not that there is none**: `Great Hornfly`, which no monster drops, is unsettled, and so is every plant or insect MHWorldData's table lacks. poedb has no gathering tables (its location pages list quests).
- `armor.hunts` is what a recipe comes down to for the builder: `[[monster id, ...], ...]`, one list per material some monster drops, and the piece can be forged once **one monster of each list** is slain. `armors/hunts.py` builds all of them in two queries (the item-monster pairs, the recipe lines) and `ArmorAPI` hands the dict to the serializer as context. A gathered material adds no list, nor does one no monster drops (a ticket, a coin); any rank and any method counts as a drop; a list that holds the whole of another is dropped, since it can never be the one that blocks (`Rath Wingtalon` beside `Rathalos Scale`). Small monsters are in the lists like any other (`Nargacuga Helm Alpha +` asks for Gajau). 1,446 of the 1,670 pieces ask for a hunt, and it adds about 117 KB to the armor list before gzip. `armors/tests.py` pins the most pieces one large monster holds alone (Great Girros, 38: its own 25 and 13 of other sets that take its sacs, hood or hide). That number is the check on `gathered`: a generic material nobody flagged ties every piece made of it to the one monster whose table names it, which is how Uragaan held 175. **The migration alone leaves every item ungathered**: `load_items` (or `seed`) has to run after it.
- Armor recipes are `armors.ArmorMaterial` (armor, item, quantity), one row per line of the recipe that forges a piece, read by `load_armors` from the `materials` key (`[{name, quantity}]`) that every row of `.dataset/armor_*.json` carries. The lines themselves are data only, like weapons: no API field and no place in the builder, and `api/v1/tests.py`'s exact armor dict and its query count are what would catch one leaking in. What the builder gets of a recipe is `hunts` (below). 6,005 lines on 1,623 of the 1,670 pieces, one to four a piece, naming 813 items. **A line that names an item not in `items.json` rolls the load back**, the `load_monsters` rule, which is why `seed` runs `load_items` before `load_armors`. The lines are in the game's order (poedb and MHWorldData print the same order on all 1,595 pieces MHWorldData has) and read back in it only because the rows order by id and the loader makes them in file order. `armor.materials` is rows, where `charm.materials` is a JSON list of the wiki's names.
- **The recipes are the game's, not the wiki's**, settled as the drop tables were: two extractions of the game files set them where they agree. poedb prints a recipe per piece (`/eng/armorset/{id}/{name}`, the "Crafting" card). Kiranico has none per piece, so its item pages are turned inside out: each lists the armor an item is used in and how many. The two agree on every one of the 1,613 pieces both have, and Kiranico's series page, which sums a set, equals the sum of the pieces on all 368 series whose page is the one asked for. MHWorldData (`armor_craft_ext.csv`, 1,595 pieces) has the same lines as poedb on every one of them, 1,584 of which are pieces here, once its Butterfly rows are read as the armor they are (below). mhw-db has recipes at Low and High Rank only (11 of its 833 Master Rank pieces have one) and differs on a single piece (`Leather Headgear Beta`: Carbalite Ore 2, where the other three have 3). The wiki was read for the pieces no dump has, and nothing else. **Scraping again needs these known.** poedb: its lists (`/eng/armors/{1..12}`) are 646 sets of which 263 are layered armor, flagged only by a `1` in the "Layered" column, some under an armor set's own name (`Banbaro α+` twice); a recipe cell also holds an `(Unlock)` tag and an `Unlock: <monster>` line, which are not materials; an empty cell is a piece that costs nothing. Kiranico: the armor index is one rarity a page (`/en/armorseries?rarity=N`; the bare URL is rarity 12 alone), 635 series of which 264 are layered, and layered pieces sit in the item pages' armor table too (`… Layered …`); the item links that open another item's page hide 118 lines, which the set totals cover, but for two lines of Kirin γ, whose series page opens another series' (one of 3, with Glavenus β+ and the festival Butterfly α); and a set total is the pieces summed, so five times the cost of a set forged as one. mhw-db spells `Coral Crystal` as `Coral Crystal - Rarity 4`. Nine base-game pieces have the wiki's name here and another in the game (`Rath Heart Vambraces Alpha` is `Rath Heart Braces α`, `Guardian Greaves Alpha +` is `Guardian Boots α+`, `Death Stench Heels` is `Death Stench Heel`): matched by hand, not renamed.
- **Two armors are called Butterfly.** One is King Beetle under its female name, forged from Great Hornfly and ore: the one in the dataset, by its skills. The other is a festival armor forged from an Insect Field Guide, whose female name is Queen Beetle and which the dataset lacks. MHWorldData's `Butterfly` rows are the festival one, so its witness for a Butterfly piece here is its King Beetle row; both of poedb's Butterfly pages print King Beetle's recipe, and Kiranico's item pages list the two under one name with two quantities. The dataset's 15 Butterfly pieces carry King Beetle's recipe.
- **A full set is forged as one, and each of its pieces carries the set's recipe**: Ryu, Ryu α, Sakura α, Leon α+ and Claire α+ (25 pieces), and Shield-Weaver +. That is how both dumps print them, and the cost is paid once for the five, so adding a build's recipes up piece by piece counts it five times. Diver, Harvest and Artemis α+ only look the same: their pieces share a recipe and are forged one at a time. 10 pieces stand on the wiki alone, Banuk α+ and Shield-Weaver +, the PlayStation-only Horizon armor that no dump of the PC game has.
- **47 pieces have no lines, for three reasons the table does not tell apart.** 11 the dumps list with an empty recipe: Guardian α+, Origin and `Dragonseal Earrings`, handed out or forged for nothing. 3 are arena rewards (`Acrobat Earrings Alpha +`, `Showman Earrings Alpha +`, `Pulverizing Feather`): that is the wiki's word, and the dumps hold only a layered armor of the same name, whose recipe is not the piece's. 33 no source has a recipe for, and no dump knows as armor at all: five "+" sets in the base-game files (Anja, Banbaro, Beo, Girros and Legiana, rarity 9 where they have one, with no slots), Direwolf, which the dumps have as a layered set only, and `Ingot Gloves`, `Ingot Faulds`, `Ingot Leggings`. Their wiki pages are placeholders (`Material x ??`), six of their `url`s open another piece's page (`Legiana Mail +` opens `Harvest_Tronco`), and they are probably not armor the game has. `armors/tests.py` pins the 47. The other way round, the dumps have 61 pieces of 13 sets the dataset lacks: Orion, Azure Age α+, Defender α, Samurai, both Bushi sets, Geralt α, Ciri α, the Artemis full set, the three Queen Beetle sets and `Brigade Boots β`.
- Set-bonus skills: an active tier's skill is in the Summary's Skills list, after the gear's skills (by name), and its pips are purple (`bonus`, `#b377f5`, the slot icons' jewel purple) where the gear's are brass. `SkillTotal.bonus` is how many of `level` a bonus adds, and `points` counts it. - Weapon: the first row of the equipment list, `build.weapon` (`{weaponId, decoIds}`, or `null`). **A build saved before weapons has no `weapon` key**, and `atomWithStorage` hands it back as it was saved, so every read is `build.weapon?.…` and nothing compares two builds by `JSON.stringify` of the whole: `keyOf` in `saved.ts` spells out what makes them the same set. `GET /api/v1/weapons/` sends `id, name, type, rarity, attack, affinity, defense, slots, elements, element_hidden, skill`: 400 KB, 27 KB gzipped, where every field would be 690 KB. - The set search takes the weapon as given, not as something to search for: `recommend`'s fourth argument is its id, the search starts from the weapon's slots where it started from none (the bounds add what lies ahead to the slots in hand, so nothing else in it moved), and every set comes back holding the weapon with its jewels placed. - Set search (`SetSearch`, the panel left of the armor): the wanted skills are `wantedAtom` (localStorage `wanted`), a `GrantedSkill[]` whose order is the priority and whose `level` is the target. The pure `recommend` in `recommend.ts` returns ready `Build`s (jewels placed), so the panel shows them through `computeTotals`, choosing one is one `setBuild`, and the set equal to the current build wears the selection band. **Best** = the level reached of each skill, capped at its target, compared in list order; defense breaks ties. It is exact, not a heuristic: dominated pieces are dropped, then a depth-first search is cut by bounds (the next bullet has the ones level 4 jewels took), and the old two are both needed — the per-skill one alone stops cutting past ~6 skills and a maxed 12-skill list goes from 0.2 s to 2 s (measured on the base-game catalog). `recommend.test.ts` (also `pnpm test`) holds it against a brute force over small generated catalogs, which tries every jewel in every slot. It ignores set bonuses, and the top results are near-twins of each other (same pieces, another charm): it ranks, it does not diversify.
- Level 4 jewels: the search places "+" jewels (Attack Jewel+ 4, two levels of one skill; the "Hard" ones three, Hard Botany four) and combos (Guardian/Attack 4, a level each of two skills) wherever they reach more. `fours` is the slot-4 jewels whose points, each held to its target, add up to two or more (a "+" of a wanted skill, a combo of two wanted skills), less any another one matches or beats on every skill; every other slot still gets the one small jewel per skill. `best(v, c, floor)` is the exact score of a finished set: every multiset of `fours` its level 4 slots can hold, `fill` for the rest, skipping a jewel that brings one point a small jewel in that slot would bring as well. **The tie rule is load-bearing.** The walk tries a set before the sets that hold it and more, the last jewel first, and keeps strict improvements only, so of two equal sets it keeps the one with fewer of `fours[0]`, then of `fours[1]`, and so on: no big jewel at all wins every tie (Attack Boost 1 wanted gets Attack Jewel 1, not Attack Jewel+ 4). That order survives taking one jewel out, which is what brings a chosen set back once a lock seats part of it. "Fewest big jewels" survives it too, but has to walk every tie, and made the search twice as slow with a `[4, 4]` weapon. `fours` is sorted worst first so the walk tries the best first.
- The bounds big jewels needed: `bound` counts the level 4 slots as one budget that a point costs 1 / `gain` of (`gain`: the most points the slot that brings the skill one can hold, 1 for a skill no big jewel brings), and gives each skill in turn the most that still fits, by a nested covering check (`fits`); it assumes every jewel for slots 1 to 3 is one level of one skill, as in the game. `rough` (one `fill`, each level 4 slot as `most` slots) is tried first. A level 4 slot as 2 loose points, or as a slot plus an extra point any "+" skill could take, was too loose: past 3M nodes on the twelve damage list. `ceiling` is the least of three bounds: the per-skill and loose ones above, and `whole`, the best one piece of a group brings with its slots too, every point loose. Without `whole` a group's best slots and best points come from different pieces, now that a level 4 slot is worth two, and that list took 6.8M nodes where it takes 0.24M. Where points are loose, a skill no jewel brings is held to what the pieces carry (`caps`).
- Defense races: a list whose tenth set meets every target is decided on defense, and big jewels made those far more common. When a branch can at best tie the tenth on skills it has to be tougher, so `toughest(d, need)` lets each group use only the rows tough enough (`tough` is each group's rows by defense, with running maxima, cut by a binary search). And the search makes two passes: the first keeps only sets that meet every target and walks as if the list were full of them (`all`), which is the whole answer when it finds ten; when it finds fewer it has found all there are, and the second pass looks for the rest, skipping those. The cheap twelve-skill list of `.docs/recommended-set.md` went from 2.5 s to 0.62 s.
- Measured (Node 22, Apple M1, the real catalog; before level 4 jewels, then after): six skills 23 ms, then 20 to 60; twelve damage skills at their cap 0.47 s, 0.46; the same with a `[4, 4]` weapon 0.47 s, 0.87; the cheap list 2.5 s, 0.62; 300 random lists median 2 ms, 2, p90 48 ms, 13, p99 604 ms, 133. The slowest found is the same list both times, 7.8 s, then 8.1: Partbreaker 1, Speed Crawler 1, Stamina Surge 2, Handicraft 3, Latent Power 2, Bombardier 3, Maximum Might 3, Free Elem/Ammo Up 2, Cliffhanger 1, Blast Functionality 1, BBQ Master 1, all met, 15M nodes nearly all of them one piece short of a set. And the sets are better: the damage list reaches Resentment 5 and Handicraft 3 where it reached 4 and 0, the six skills defense 900 where 896, the cheap list 760 where 702. Not done: ordering a node's children by their own bound saves a quarter to a half on the damage lists, but that order rests on the points in hand, which a lock changes, and among exact ties at tenth place another set could then win and take the band off the one chosen.
- The search is live, and **it runs in a Web Worker, not on the main thread and not on the server**: it reruns on every change to the list, capped at `MAX_WANTED`, and the page never waits on it, though the heaviest lists take seconds (above). Not the server, because the search is a tight integer loop that a JIT runs many times faster than Python, gunicorn's 3 workers would be tied up by anonymous visitors on a public page, every edit would wait on the network, and a search the input has moved past could not be stopped. `useSets` (`use-sets.ts`) owns the worker (`recommend.worker.ts`): the catalog is posted to it once, then each search is `{id, query}`, `query` being `{wanted, unslain, keep, weaponId, locked}`, and the worker narrows the pool and runs `recommend`. A new query while a search is out ends that search by terminating the worker; a new one is handed the catalog again, some 15 ms of cloning on an M1. Only the reply to the last id sent is taken. Measured in Chrome, the slowest list (7.4 s) drew 438 frames while it ran, the worst gap 33 ms, with no long task but the 55 ms of startup, and a list cut short mid-search had its new answer 100 ms later. The query is `useMemo`ed from parts that are memoized themselves, on purpose: the search goes by identity, so a part rebuilt each render would search each render. In dev StrictMode runs the effect twice, and the second ends the first's worker. Vite bundles the worker as its own chunk (`recommend.worker-*.js`, 7 KB), loaded from `/assets` like the rest, so nginx needs nothing.

- Lock: `lockedAtom` (localStorage `locked`) is the rows of the equipment list the set search has to keep, a `Lockable[]` (`weapon`, the five armor types, `charm`). A locked row is a group of one in the search, **with no blank beside it**: a locked charm with none of the wanted skills is the blank's equal, and `prune` keeps the earlier of two equal rows. The skills of its jewels are points in hand, whatever the jewel, so a combo jewel there counts for both its skills. A locked weapon starts the search from its jewels' points and its empty slots; unlocked, it is as before. The heart is `brass`, not `ember`: below `md` it is the whole control and has to hold 3:1 on the backdrop, which `ember` just misses by the arithmetic that puts `moss` at 4.5:1. Its `-m-2 p-2` is a 32px tap area that stops 8px short of `Clear set`, which has no undo. **Playwright's Chromium draws a 15px scrollbar**, so a 320px viewport there is a 305px page and the title is on four lines with or without a second control: compare the header's width, not the viewport's.
- Share card: `frontend/public/og.jpg` (1200×630, 230 KB) is what a shared link previews with, named by the static `og:` tags in `frontend/index.html`. Crawlers run no JavaScript and every route serves that one file, so every URL of the site shares the card. **The tags' URLs are absolute and hardcoded to `https://mhwbuilder.com`**, since several crawlers take no relative one: another domain means editing them. The image is a screenshot of `frontend/og.html`, which the dev server serves at `/og.html` and the build, whose only input is `index.html`, leaves out. That page links `/src/styles.css` and is written in the app's own utilities (`smithy`, `frame`), so it follows the look without a copy of the tokens; Tailwind scans it like any file, and its classes cost the production CSS 1.3 KB (0.2 KB gzipped). To redraw: a 1200×630 viewport at device scale 1, wait for the fonts and the images, screenshot, then `sips -s format jpeg -s formatOptions 88`. It is a JPEG kept under 300 KB because that is the size past which WhatsApp is reported to drop the image, and WebP is not safe with every crawler. **The set on it is transcribed, not live**: the search's first answer for Critical Eye 7, Weakness Exploit 3 and Attack Boost 4 (the Fatalis pieces, which the dataset calls `Dragonhead Alpha +`), three of its six skills, no charm, so a change to the dataset or the search does not reach it. Its armor and skill icons are hotlinked from the wiki at the moment of the screenshot, so one the host refuses is an empty plate in the image. The slot icons are 48px, twice the files' 24: they are pixel squares, and any size but a multiple breaks the grid. Crawlers cache the image, so a changed card needs a new file name. A missing `og.jpg` does not 404 (nginx falls back to `index.html`): the symptom is a preview with no image.
- Favicon: `frontend/public/favicon.svg` (315 bytes) is the source, and `favicon.ico` (32×32) and `apple-touch-icon.png` (180×180) are rasters of it; three `<link>`s in `frontend/index.html` name them. The mark is lucide's `Shield`, the one beside Defense in Status: the path of lucide-react 1.14, copied in and **filled, not stroked**, in `brass` on a `hide` plate. A fill holds its shape in a tab's 16px, where the icon's 2px stroke would be 1.3. The two colours are written out as hex, since a favicon reads none of the page's tokens: a changed token does not reach it. The plate is opaque on purpose: brass alone is 1.9:1 on a white tab bar and 10.7:1 on `hide`. `sizes="32x32"` on the `.ico`'s link is what lets a browser that takes an SVG icon prefer it (the known behaviour; not compared in a browser here). The `.ico` is for what takes no SVG icon, and for a page that names no icon, where a browser asks for `/favicon.ico` on its own: Django's `/admin/`, which shares the origin (not looked at through nginx here). The touch icon is not the SVG as it is: its plate has square corners (no `rx`) and its shield is at 80% about the centre (`transform="translate(12 12) scale(.8) translate(-12 -12)"`). iOS rounds the icon itself and paints transparency black (the known behaviour; no device here), and a home-screen icon wants more margin than a tab's. To redraw, give a copy of the SVG `width="512" height="512"`, the size `sips` then rasterizes it at: `sips -s format png`, then `sips -z 32 32` and `sips -s format ico` for the `.ico`, and the same from the square variant with `sips -z 180 180` for the touch icon. No script is committed, as with the slot icons. `sips` leaves an alpha channel in the PNG, and every pixel of the touch icon is opaque all the same. **A missing icon does not 404**: nginx, and Vite's dev server too, answer 200 `text/html`, which is what `/favicon.ico` got before the file existed, so the check is the content type and not the status. There is no web manifest and no 192 or 512px icon: the site is not installable.
- Loading screen: `LoadingScreen` (`frontend/src/components/loading-screen.tsx`) is one picture for three waits in a row, so nothing flashes between them. `index.html` draws it in inline styles, as `#boot`, until the script has run; the router shows it while a route's chunk loads (`defaultPendingComponent`); the builder shows it, as "Loading the armor list…", while the catalog loads. `#boot` lies **over** `#root`, not in it: React empties `#root` on its first commit and the router's first match comes a frame later, which in `#root` was one white frame between two dark screens. `AuthGate` removes it on mount, the moment the router has drawn something of its own. `defaultPendingMs: 0` is measured: with the router's default second the page is blank from React's mount until the chunk arrives, 0.6 s of white on slow 4G. `defaultPendingMinMs` is left at its default: it reads in the router's source like a 500 ms hold on every first load, and no such hold happens (pending to page is 10-14 ms). The look lives in two places, the component and `index.html`'s inline style: change both.
- The search's wait: `searching` in `SetSearch` is true while the answer on screen is not the current query's (`answer?.query !== query`), and never with an empty list, which `useSets` answers itself without a search. Everything that reads the sets reads them with the query they answer (`answer.query`): what a set falls short on, and whether a set clicked before the search caught up keeps the rows locked since. The sets then carry `aria-busy` and dim to 60%, and with no sets yet a "Searching for sets…" line stands where they will be. Both hold back 200 ms (a transition delay, an animation delay): most searches are done by then, and a sign that shows for a frame is a flicker. Measured in Chrome: a fast search is busy for some 50 ms and never dims; a 6.5 s one dims from 250 ms and comes back the moment its answer lands. A worker's error answers with no sets, so the line never stays for good.
- Not found: an address no route answers gets `NotFoundPage` (`frontend/src/components/not-found.tsx`), the root route's `notFoundComponent`. `AuthGate` reads `globalNotFound` off the router's matches and, when it is set, redirects nowhere and renders the bare `<Outlet />`: without that a logged-out visitor is sent to `/login`, and a signed-in one gets the page inside `AppShell`. **The response is still a 200**: nginx's `try_files` sends `index.html` for any path, and that is left alone on purpose. A real 404 needs the router's routes copied into `nginx.conf`, and a route missing from the copy would answer 404 for a real page. So the page carries `<meta name="robots" content="noindex">`, which React lifts into `<head>` and takes out on the way back to a real page.
- Page titles: `PageTitle` (`frontend/src/components/page-title.tsx`) renders a `<title>`, which React inserts ahead of `index.html`'s and removes on unmount, so the first `<title>` in the document, the one a browser uses, is the page's. `/` renders none: its title is `index.html`'s, the only one a crawler that runs no script ever sees, along with the description. A new page without a `PageTitle` shows the site's title. There is no description per page: only `/` is indexable.
- Crawlers: `frontend/public/robots.txt` and `frontend/public/sitemap.xml` are static files, and reach a crawler as files because `try_files` tries `$uri` first. The sitemap lists `/` alone, the one indexable page: a new public page goes into it by hand. robots.txt keeps crawlers off `/admin/` and the template's `/login`, `/dashboard` and `/onboarding`, and **leaves `/api/` open on purpose**: the page is drawn from `/api/v1/`, and a crawler barred from it indexes the loading screen. Both files carry the origin `https://mhwbuilder.com`, as the `og:` tags do: three files to edit for another domain.
- Analytics: two `defer` tags in `frontend/index.html`'s `<head>`, a self-hosted Umami at `umami.jordanmaulana.space`: the tracker (`script.js`), then the session recorder (`recorder.js`, rrweb, 191 KB), in that order because the recorder waits for the tracker's session. Every route serves that one file, so every page has both, `/login` included. The tracker patches `history.pushState`, so the router's navigations are counted with no code in the app. **The recorder takes nothing from the page but the website id**: whether it replays, the heatmap, the sample rate (15% unless set) and the mask level (`moderate` unless set) are the Umami dashboard's, fetched from `/api/websites/{id}/recorder`. **Dev visits are counted too** (`make web`, a browser test): the tracker's `data-domains` attribute would hold it to one hostname and is not set, since it matches exactly and a visit on `www.` would silently stop counting. Page views only: no custom event is sent yet.
- Not modelled: secret-skill caps and Iceborne sets. `sets.json` is scraped from the wiki's base-game set comparison page, so the other 45 set bonuses have no tiers and no armors — no Master Rank piece has a set bonus — and skills cap at `max_level`. For weapons: Low and High Rank, what is particular to a weapon type (shelling, phials, horn notes, kinsect bonus, coatings, ammo), Safi'jiiva awakenings and augments; and in the builder, anything a weapon does but hold jewels and add its defense bonus: its own skill is named and not counted (not even Critical Element and Critical Status, the two that are in the skill catalog), attack and affinity are the weapon's own numbers with no skill applied, and sharpness and elderseal are not shown. For monsters: what one inflicts, its resistances, locations, HP and hitzones; capture as its own table; Kulve Taroth's appraisal weapons and the 11 tables of hers no source labels; 17 small-monster quest rewards that only one source has (16 of them poedb's, at Master Rank); event-quest rewards. For armor recipes: the zenny a piece costs, which only the wiki has; layered armor; upgrade and augment costs; where a coin or a ticket comes from. For items: the ones that no monster drops and no armor is forged from. For unslain monsters: rank (a monster is slain or not, so one slain at High Rank counts for its Master Rank armor too, and nothing holds back Master Rank ore armor from a hunter who is not there yet); charms, whose materials are not linked to items, so a set can still name a charm that needs an unslain monster; the quests that pay an item though its target's tables lack it (`Pure Dragon Blood` from Alatreon's and Fatalis's), which would only add monsters to a list, never take one away; and tickets and coins, which count as had. For locks: who put a jewel on a locked row, the hunter or the search. Both are kept alike, so the jewels of a skill since taken off the wanted list stay on a locked row until they are removed by hand; and there is no way to keep a piece out of the sets, only in.

## Auth + frontend flow (read before touching login/onboarding/routing)

- Endpoints: `api/v1/auth_api.py` — `POST /auth/google/`, `POST /auth/register/`, `POST /auth/login/` each return `{ token, user }`; `GET /auth/me/` rehydrates the user from the token; `POST /auth/logout/` deletes the token.
- The user shape is `UserSerializer` in `api/v1/serializers.py` → `{ id, email, onboarded }`. Frontend mirror: `AuthUser` in `frontend/src/features/auth/types.ts`.
- **Routing is centralized in `AuthGate`** (`frontend/src/features/auth/components/auth-gate.tsx`) — the single source of truth for redirects:
  - No token + not on a public path (`/`, `/login`) → `/login`.
  - Token + `!onboarded` → `/onboarding` (the opt-in gate; dormant by default).
  - `onboarded` + on `/login` or `/onboarding` → `/dashboard`. **Not** on `/`: that is the public armor builder, and signed-in users may stay on it.
- **`onboarded` source of truth** = `get_onboarded` in `api/v1/serializers.py`. **It defaults to `True`** so a fresh template runs `login → dashboard` out of the box. The `/onboarding` page (`frontend/src/routes/onboarding.tsx`) is an optional placeholder and is unreachable while `onboarded` is always true.

### Enabling a real onboarding step

Previously the template trapped users in onboarding because `get_onboarded` read a non-existent `profile` model and always returned false with no way to complete it. To build a working onboarding flow, change **all four** touch-points in one pass:

1. **Model**: create an `accounts` app (`uv run manage.py startapp accounts`), add `"accounts"` to `INSTALLED_APPS` in `core/settings.py`, define `Profile(BaseModel)` (e.g. `full_name`, `OneToOne` to `User`) in `accounts/models.py`, then `make mmg && make migrate`. Do **not** put this in `core/models.py` (see [App structure](#app-structure-where-models-go)).
2. **Serializer**: `get_onboarded` in `api/v1/serializers.py` returns the real state (e.g. `bool(obj.profile.full_name)`).
3. **Endpoint**: add a PATCH/POST in `api/v1/auth_api.py` (wired in the v1 urls) that fills the profile / flips the flag.
4. **Frontend**: build the form in `frontend/src/routes/onboarding.tsx` to call that endpoint, then refetch `me()` so `AuthGate` redirects to `/dashboard`.

## Docker

Three services in `docker-compose.yml`, all driven by `.env.docker` (`make dock`, `./update.sh`):

- `postgres` — 16-alpine, `pgdata` volume. Its `POSTGRES_*` vars use `${VAR:?...}`, so a bare `docker compose up` **aborts** instead of initdb'ing a cluster with throwaway credentials the backend can't log into. `initdb` runs once on an empty data dir and `down` keeps the volume, so that mistake is not fixable by restarting — only `ALTER ROLE` or `down -v`.
- `backend` — `Dockerfile.backend`, gunicorn on :8000, **not published**. Non-root (uid 10001), venv on `PATH` so the runtime command is bare `gunicorn` / `python manage.py` (no `uv` in the image). Its `node:20-alpine AS tw` stage is **not** the SPA build — it compiles Tailwind for Django's own `templates/` from the **root** `package.json`.
- `frontend` — `frontend/Dockerfile` (pnpm build → `nginx:alpine`), published on **`127.0.0.1:$FRONTEND_PORT`** (8014) only. Put a reverse proxy / tunnel on the host in front of it.

**The two are ONE origin.** `frontend/nginx.conf` proxies `/api/`, `/admin/` and `/static/` to `backend:8000`; everything else falls through to the SPA. So:

- `VITE_API_URL` is **unset** — `frontend/src/lib/api.ts` builds `${VITE_API_URL ?? ""}/api/v1`, i.e. relative `/api/v1`. The built image is environment-agnostic; don't reintroduce an absolute API URL.
- **CORS is inert**, but `DJANGO_CORS_ALLOWED_ORIGINS` is still load-bearing: it feeds `CSRF_TRUSTED_ORIGINS`, and without the real public origin admin POSTs fail with "Origin checking failed".
- `/admin/` is reachable **only through nginx** (`http://localhost:$FRONTEND_PORT/admin/`) since the backend port isn't published.
- `SECURE_PROXY_SSL_HEADER` in `core/settings.py` trusts `X-Forwarded-Proto`, which nginx passes through from upstream (**not** `$scheme` — nginx is reached over plain HTTP, so `$scheme` would silently defeat it). That trust is only safe while the backend port stays unpublished.
- nginx resolves the literal `backend` hostname at config load, hence `depends_on: {backend: service_healthy}`. That chain makes `DJANGO_ALLOWED_HOSTS` load-bearing too: it must include `localhost,127.0.0.1` for the backend healthcheck, or the backend sits `unhealthy` forever and `frontend` never starts — symptom is a dead site, not a red check.

Healthchecks hit `127.0.0.1`, never `localhost`: in `nginx:alpine` `localhost` is `::1`, nginx listens on `0.0.0.0:80`, and busybox `wget` won't fall back to IPv4.

`try_files … /index.html` in `frontend/nginx.conf` keeps client-side routes (`/dashboard`, `/login`) alive on a hard refresh — don't drop it. Django's own `/login/`, `/dashboard/` template views are scaffolds and are deliberately not proxied.

`VITE_*` are **build args**, inlined by Vite at build time: changing one needs `docker compose build frontend`, not a restart.

Dev loop mirrors prod — `make web` runs Vite on :5173 and proxies `/api`, `/admin/` and `/static/` to a local backend on :8000, so dev is one origin too (admin at `http://localhost:5173/admin/`).

Container ops: `make sh` (shell into backend), `make mg CMD="createsuperuser"` (manage.py in the container), `make backup` (verified `pg_dump` into `./backups`, keeps the last 14).

Two things that must stay true or the image build breaks:

- `frontend/src/routeTree.gen.ts` is **committed**, not gitignored. `pnpm build` is `tsc -b && vite build`; `tsc -b` runs first and fails on a fresh clone if the generated route tree is absent.
- `.dockerignore` (root and `frontend/`) excludes `.venv/`, `node_modules/`, `dist/`, `db.sqlite3`, and `.env*`. A stray `.env` inside the backend image would win over compose's env — `core/settings.py` calls `load_dotenv(..., override=True)`.
